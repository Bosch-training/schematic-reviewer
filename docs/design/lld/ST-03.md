# LLD ST-03: Confidentiality-safe logging

## 1. Purpose

Provide one `log_event` helper that is the only sanctioned way to log. It accepts only allow-listed fields (`review_id`, `finding_id`, `status`, `error_type`) so document content, annotation text and extracted data cannot reach a log record (story ST-03; architecture section 9; AGENTS.md NFR-07 rule). Deterministic, no I/O beyond the standard logger.

## 2. File tree

```
safe_logging.py            # log_event, configure_logging
tests/test_safe_logging.py
```

Location and name are an assumption (open questions 1, 2). A root file `logging.py` is avoided because it would shadow the stdlib module.

## 3. Public signatures

```python
ALLOWED_FIELDS: frozenset[str] = frozenset(
    {"review_id", "finding_id", "status", "error_type"}
)
LOGGER_NAME: str = "schematic_review"

def configure_logging() -> None: ...

def log_event(event: str, /, **fields: object) -> None: ...
```

`event` is positional-only so a field named `event` cannot collide with it. `configure_logging` takes no arguments: level and format are not specified by any source (open question 3).

## 4. Data structures

- `ALLOWED_FIELDS`: immutable allow-list, the single source of truth for permitted keys.
- Allowed fields are attached to the record through `extra=fields`, so each appears as a record attribute (`record.review_id`). None of the four names collides with a reserved `LogRecord` attribute.

## 5. Steps

`log_event(event, **fields)`:

1. Compute `rejected = sorted(fields.keys() - ALLOWED_FIELDS)`.
2. If `rejected` is not empty, raise `ValueError` naming the rejected keys only. The message never contains field values. Nothing is logged.
3. Emit `logging.getLogger(LOGGER_NAME).info(event, extra=fields)`.

`configure_logging()`:

1. Get the `LOGGER_NAME` logger.
2. If it has no handlers, add one `StreamHandler` with a formatter that prints the message and the allowed fields that are present.
3. Leave `propagate` at its default `True` so `caplog` and root handlers still receive records.
4. Idempotent: calling twice adds no second handler.

## 6. Error and `Unable to Verify` handling

- Any key outside `ALLOWED_FIELDS` raises `ValueError` before emission, so a rejected call leaves no record (fail closed).
- `log_event` takes no `exc_info`, `stack_info` or exception object, so tracebacks that may carry content are not logged. Callers pass `error_type` (class name string) only.
- The helper makes no Pass/Fail decision. `status` is passed through as given and is never defaulted, so a missing status is not recorded as `Pass`.
- Limit: only keys are checked. A caller can still place content in an allowed value or in `event` (open question 4).

## 7. Test plan (keyed to story analysis section 3)

| Test | Covers |
|---|---|
| T-01 | Each allowed key appears as a record attribute with its value. |
| T-02 | `text=` raises `ValueError`; no record emitted. |
| T-03 | Mixed allowed and disallowed keys: rejected, message lists only the bad key names, sorted. |
| T-04 | Exception message does not contain the rejected value. |
| T-05 | `log_event("x")` with no fields succeeds. |
| T-06 | `event=` passed as keyword is rejected (positional-only). |
| T-07 | `configure_logging()` twice leaves one handler. |
| T-08 | Records propagate (visible to `caplog`). |
